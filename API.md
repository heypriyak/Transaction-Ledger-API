# API documentation

All responses are JSON. Errors have the consistent shape:

```json
{"error":{"code":"VALIDATION_ERROR","message":"...","details":null}}
```

### `GET /`

Returns a service health response and links to the main API resources.

## Accounts

### `POST /accounts`

Creates an account. Body: `{ "name": "Operating Account" }`. Returns `201`.

### `GET /accounts?page=1&limit=20`

Lists accounts with `data` and `pagination` (`current_page`, `page_size`, `total_records`, `total_pages`).

### `GET /accounts/:accountId`

Returns an account and its current integer balance.

## Transactions

### `POST /accounts/:accountId/transactions`

Creates an immutable credit or debit atomically with the balance update.

```json
{
  "type": "credit",
  "amount": 1000,
  "description": "Invoice payment",
  "reference_id": "invoice-001"
}
```

`type` is `credit` or `debit`; `amount` must be positive; `reference_id` is unique per account. Debit requests with insufficient funds return `409 INSUFFICIENT_BALANCE`. Duplicate references return `409 DUPLICATE_TRANSACTION`.

### `GET /accounts/:accountId/transactions?page=1&limit=20`

Lists transactions latest-first by `created_at` (with `id` as a deterministic tie-breaker), plus pagination metadata.

There are intentionally no update or delete transaction endpoints.

## Transfers

### `POST /transfers`

Atomically debits the source and credits the destination:

```json
{
  "source_account_id": 1,
  "destination_account_id": 2,
  "amount": 300,
  "reference_id": "transfer-001",
  "description": "Settlement"
}
```

Both accounts must exist, differ, and the source must have sufficient balance. The API records one debit and one credit transaction and rolls back all changes if either insert fails.

## Assumptions

- Money is represented as positive integer minor units, such as cents.
- SQLite is the local relational database; foreign keys, checks, and a per-account reference uniqueness index enforce integrity.
- Transaction timestamps are generated by the server and cannot be supplied or changed by clients.
- Transfer references are expanded to `reference_id:debit` and `reference_id:credit` so each ledger entry remains unique per account.
